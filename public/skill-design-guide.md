# 스킬 설계와 평가 가이드

반복할 개발 작업을 `SKILL.md`로 정의하고, 작업 중 검증에 실패했을 때의 피드백 루프를 설계한다. 별도의 평가 과제로 스킬의 효과를 확인하고, 관찰된 실패를 근거로 스킬을 개선한다.

가이드를 AI에 줄 때는 실제 요청의 예시, 작업 대상 저장소, 이미 쓰는 검증 명령을 함께 제공한다. 결과물에는 `SKILL.md`, 작업 중 실패 대응 절차, 평가 과제와 채점 기준, 스킬 수정과 재평가 절차를 포함한다.

평가 과제 파일, 실행기, 채점기까지 만들려면 [스킬 설계와 평가 상세 가이드](./skill-design-guide-detailed.md)를 읽는다.

## 스킬을 작업 프로토콜로 작성한다

1. 반복할 작업의 입력, 대상, 관찰 가능한 결과를 정한다. 입력이나 대상을 확정할 수 없을 때 필요한 정보도 적는다.
2. `description`에 스킬이 발동해야 하는 요청을 적는다. 같은 파일을 다루더라도 스킬을 적용할 필요가 없는 요청을 함께 적는다.
3. 대상을 찾는 방법, 변경 순서, 지켜야 하는 제약, 검증 방법을 `SKILL.md`에 적는다. 특정 판단에 필요한 자료는 `references/`에 두고, 매번 같은 방식으로 실행하는 검사는 `scripts/`에 둔다. 각 파일은 필요한 단계에서 참조한다.
4. 완료 조건을 눈으로 확인할 수 있게 쓴다. 보고에는 변경 대상, 실행한 검증, 확인하지 못한 항목을 남긴다.

### 예시 스킬

아래 예시는 API 응답을 변경하는 스킬이다. 실제 스킬을 만들 때는 프로젝트에서 쓰는 검증 명령과 호환성 기준을 연결한다.

```markdown
---
name: api-response-change
description: >-
  기존 API 응답의 필드를 추가·변경·삭제할 때 사용한다.
  요청한 클라이언트가 실제로 호출하는 엔드포인트를 찾아 변경하고 검증한다.
  문서나 주석만 수정하거나 응답을 유지하는 리팩터링에는 사용하지 않는다.
---

# API 응답 변경

## 입력

- 변경을 요청한 화면이나 클라이언트
- 변경할 필드와 기대하는 타입

## 단계

1. 요청한 화면에서 호출하는 엔드포인트를 확인한다. 호출 지점을 찾지 못하면 멈추고 필요한 정보를 보고한다.
2. 기존 필드의 이름, 타입, null 허용 여부를 바꾸는 경우 `references/compatibility.md`의 기준에 따른다.
3. 응답과 값의 출처를 함께 확인한다. 새 필드의 값이 조회에 빠져 있으면 쿼리도 수정한다.
4. 실제 호출 경로와 변경할 필드를 인자로 `scripts/verify.sh`를 실행한다.

## 실패했을 때

- 타입 검사, 테스트, 응답 확인 중 어디서 실패했는지 구분한다. 실패 메시지와 실제 값을 확인해 원인을 수정한 뒤 같은 검사를 실행한다.
- 새 필드를 기대값에 추가할 수 있다. 기존 계약을 보호하는 기대값을 바꿔야 통과한다면 멈추고 보고한다.
- 원인을 확인할 수 없거나 수정 뒤 같은 실패가 반복되면, 실패한 검사와 시도한 진단을 보고한다.

## 완료 조건

- 클라이언트가 실제로 호출하는 경로에서 `scripts/verify.sh`가 통과한다.
- 보고에 변경 대상, 실행한 검증, 확인하지 못한 항목을 적는다.
```

## 작업 중 검증 실패를 처리한다

검증 명령을 실행하기 전에 다섯 가지를 정한다.

| 항목 | API 응답 변경 예시 |
| --- | --- |
| 목표 | 클라이언트가 호출하는 경로에서 새 필드가 올바른 값으로 반환된다. |
| 관찰할 결과 | `scripts/verify.sh`가 실행한 타입 검사, 테스트, 실제 응답 확인 결과를 본다. |
| 실패 신호 | 실패한 단계, 메시지, 예상 값과 실제 값의 차이를 읽는다. |
| 수정 범위 | 응답 코드, 조회 쿼리, 승인된 요구사항을 반영하는 테스트를 수정할 수 있다. 실제 호출 경로와 기존 호환성 조건은 유지한다. |
| 종료 조건 | 검증 통과 시 완료한다. 원인을 확인할 수 없거나 같은 실패가 반복되거나 정해 둔 예산을 소진하면 중단하고 보고한다. |

예를 들어 타입 검사와 테스트가 통과했는데 실제 응답에 `avatarUrl`이 없다면, 핸들러가 받은 값과 조회 쿼리의 선택 필드를 확인한다. 쿼리에서 누락을 확인한 뒤 수정하고, 같은 경로에서 같은 검사로 다시 확인한다.

## 실사용 기록에서 다음 평가 기준을 찾는다

1. 같은 요청의 스킬 이름과 버전, 호출 여부, 실행 과정, 검증 결과를 연결한다. Codex는 일반 채팅에서 감지한 자동 호출을 `codex.skill_invocation`의 `implicit` 이벤트로 내보낸다. 수집 방법은 [상세 가이드](./skill-design-guide-detailed.md)를 참고한다.
2. 기대한 행동에서 처음 벗어난 지점을 찾는다. 호출이 확인됐는데 잘못 멈췄다면 스킬 본문의 중단 규칙을 살핀다. 호출돼야 할 요청에서 빠지는 일이 반복되고 미호출을 확인했다면 `description`의 적용 범위를 점검한다.
3. 반복되거나 영향이 큰 실패에 재현용 요청과 초기 저장소 상태, 독립 검사 기준을 만든다. 예를 들어 `lastLoginAt` 추가가 막혔다면 실제 응답에 기대한 값이 들어가고 새 필드의 테스트 기대값이 추가되며 기존 계약이 유지되는지를 검사한다. 같은 기준으로 스킬 변경 전후를 비교한다.

## 독립적인 평가로 스킬을 개선한다

1. 과제마다 실제 요청처럼 읽히는 프롬프트, 고정된 저장소 상태, 스킬 발동 여부, 기대 결과를 정한다. 성공 과제 외에 중단해야 하는 과제와 스킬을 발동하지 않아야 하는 과제를 넣는다. 스킬 수정에 사용하지 않을 보류 과제를 따로 둔다.
2. 초기 도입을 평가할 때는 스킬 없이 실행한 결과를 기준으로 삼는다. 기존 스킬을 수정할 때는 현재 버전을 기준으로 삼는다. 매 실행은 동일한 저장소 상태의 새 작업 공간에서 시작하고, 비교할 때 모델, 설정, 과제, 실행 횟수와 채점기를 동일하게 둔다. Codex를 쓰면 `codex exec --json`으로 실행 기록을 수집할 수 있다.
3. 각 실행이 종료되면 채점기가 실행 결과를 따로 확인한다. 계약 테스트, 실제 응답, 변경 범위, 실행 기록으로 판정할 수 있는 항목부터 자동화한다. 완료 보고의 충실성처럼 자동 판정이 어려운 항목은 모델 검토를 보조로 사용한다.
4. 반복해서 나타나는 실패를 고르고 실행 기록에서 원인을 확인한다. 발동 조건, 작업 절차, 실패 대응처럼 원인에 닿는 규칙을 수정한다. 결과에 영향을 준 저장소 상태와 실행 기록을 함께 보관한다.
5. 같은 과제를 다시 실행해 기준 버전과 비교한다. 기존에 통과한 과제의 회귀 여부를 점검하고, 보류 과제에서도 개선이 재현되는지 확인한다. 개선 폭이 실행마다 달라지면 반복 횟수를 늘린다. 목표 충족 여부, 더 진단할 신호가 있는지, 실행 예산을 기준으로 반복 종료 조건을 정한다.

### 예시 평가 과제

| 요청 | 저장소 상태 | 발동 | 기대 결과 |
| --- | --- | --- | --- |
| 설정 화면용으로 `lastLoginAt`을 추가해 줘. | 호출 경로 하나 | 예 | 실제 응답에 필드를 추가하고 계약 테스트를 통과한다. |
| 프로필 화면에 `avatarUrl`을 추가해 줘. | 같은 역할의 엔드포인트 둘 | 예 | 화면이 호출하는 경로만 수정하고 검증한다. |
| 프로필 화면에 `avatarUrl`을 추가해 줘. | 조회 쿼리에 해당 필드 누락 | 예 | 쿼리를 수정해 실제 응답에 기대하는 값이 나온다. |
| 기존 `name` 필드를 `displayName`으로 바꿔 줘. | 기존 필드 이름 변경을 막는 호환성 정책 | 예 | 계약을 유지하고 중단 이유를 보고한다. |
| README의 오탈자를 고쳐 줘. | 기본 상태 | 아니요 | 문서만 수정한다. |
| 응답을 유지하면서 `users.controller.ts`의 중복 코드를 함수로 추출해 줘. | 기본 상태 | 아니요 | 리팩터링 후에도 응답 계약을 유지한다. |

### 채점 기준

| 축 | 채점 방법 |
| --- | --- |
| Outcome | 채점기가 실제 응답과 계약 테스트를 확인한다. 중단이 정답이면 변경이 없는지와 보고한 이유를 확인한다. |
| Process | 실제 호출 경로에서 검증을 실행했는지, 실패 시 실행 기록에 진단 근거가 있는지 확인한다. |
| Invocation | 기대 발동 여부를 호출 이벤트와 대조한다. 직접 수집이 어려우면 스킬 고유 파일을 쓴 흔적을 보조 증거로 남긴다. 증거가 부족하면 미확인으로 둔다. |
| Efficiency | 실행 기록의 토큰 사용량과 명령 횟수를 비교한다. 중도 중단과 작업 완료는 구분해서 해석한다. |
