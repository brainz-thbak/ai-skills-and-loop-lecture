title: 피드백 루프는 단순한 재시도가 아닙니다

2장의 스킬을 저장소에 추가하고, 서론과 같은 요청을 Codex에 다시 맡겨 보겠습니다. “프로필 화면에 이미지가 보이도록 사용자 조회 API에 `avatarUrl`을 추가해 줘.”

이번에는 스킬의 1·2단계에 따라 프로필 화면의 데이터 요청 코드부터 확인하므로, Codex는 `GET /users/:id`를 찾아 `users.controller.ts`의 응답에 `avatarUrl`을 추가합니다. 서론과 같은 실수는 하지 않았습니다. 그런데 5단계에서 실행한 `verify.sh`가 실패합니다.

스킬의 '실패했을 때' 항목에는 “대상 엔드포인트를 바꾸지 말고 원인을 고친다”는 한 줄뿐입니다. 원인을 어떻게 찾고, 고친 뒤 무엇을 확인하며, 언제 멈추는가. 이 장에서 다룰 피드백 루프입니다.

### 실패 메시지를 따라간 기록

<p class="keep-with-next">Codex가 <code>verify.sh</code>를 통과하기까지의 기록입니다.</p>

```bash 루프 기록
# 시도 1
$ scripts/verify.sh /users/42 avatarUrl
 FAIL  src/legacy/users.controller.test.ts > GET /users/:id
AssertionError: expected { id: '42', name: 'Kim', …(1) } to deeply equal { id: '42', name: 'Kim' }
# 진단: 응답 전체를 비교하는 기존 테스트가 새 필드 때문에 실패했다
# 조치: 기대값에 avatarUrl을 추가한다. 기존 필드의 기대값은 그대로 둔다

# 시도 2
$ scripts/verify.sh /users/42 avatarUrl
FAIL: /users/42 응답에 avatarUrl 값이 없음 (null 포함)
# 진단: 조회 쿼리가 avatar_url 컬럼을 읽지 않는다
# 조치: users.repository.ts의 SELECT에 avatar_url을 추가한다

# 시도 3
$ scripts/verify.sh /users/42 avatarUrl
OK: /users/42 응답에 avatarUrl 있음
```

세 번 시도하는 동안 대상 엔드포인트는 그대로였고, 고친 곳은 매번 실패 메시지가 가리킨 위치였습니다. 시도 2의 `null`은 1장에서 본 바로 그 문제입니다. 컨트롤러 테스트는 저장소를 목으로 바꿔 두었기 때문에 통과했지만, 실제 서버를 호출하는 `verify.sh`에서는 드러났습니다. 스킬의 3단계에서 놓친 부분을 5단계가 잡아낸 것입니다.

‘다시 해 줘’나 ‘좀 더 꼼꼼히 봐 줘’도 다음 시도로 이어지기는 합니다. 차이는 다음 시도가 어디서 출발하느냐입니다. 위 기록의 각 시도는 직전의 실패 메시지에서 출발했고, 실패의 내용이 매번 바뀌었으므로 진전이 있다고 판단할 수 있었습니다. 실패의 내용을 출발점으로 삼지 않으면, 같은 작업을 되풀이하는 재시도에 그칩니다.

### 루프를 이루는 다섯 가지

이 반복이 재시도가 아니라 루프였던 것은 다섯 가지가 갖춰져 있었기 때문입니다. 도달할 **목표**(`GET /users/:id`로 `verify.sh` 통과), **관찰할 결과**(`verify.sh`의 출력), **해석할 수 있는 오류 신호**(실패 메시지), **조정할 대상**(코드. 대상 엔드포인트는 그대로), **종료 조건**(통과하거나, 판단할 수 없으면 멈추고 보고)입니다.

### 실패 메시지로 진단하기

그림의 FAIL 칸, 즉 실패 메시지에서 원인을 찾아 고치는 과정은 네 단계로 나눌 수 있습니다.

**1. 어느 검사가 실패했는지 구분합니다.** `verify.sh`는 타입 검사, 테스트, 응답 확인을 차례로 실행합니다. 어느 단계에서 멈췄느냐에 따라 메시지가 알려 주는 것과 먼저 볼 곳이 다릅니다.

| 실패한 단계 | 메시지가 알려 주는 것 | 먼저 볼 곳 |
|---|---|---|
| 타입 검사 | 타입이 어긋난 파일과 줄 | 메시지가 가리키는 줄 |
| 테스트 | 실패한 테스트, 기대값과 실제값의 차이 | 그 차이가 새 요구사항 때문인지, 기존 동작이 바뀐 탓인지 |
| 응답 확인 | 실제 서버의 응답에 값이 없다는 사실 | 응답을 만드는 코드에서 값이 어디서 오는지 |

**2. 통과한 검사로 범위를 좁힙니다.** 통과한 검사도 정보입니다. 시도 2에서는 타입 검사와 테스트가 통과하고 응답 확인만 실패했습니다. 테스트가 확인한 범위에는 원인이 없다는 뜻이므로, 테스트가 확인하지 않은 곳, 곧 목으로 대신한 저장소 계층부터 의심합니다.

<p class="keep-with-next"><strong>3. 값이 어디서 오는지 거슬러 올라가며 직접 확인합니다.</strong> 추측으로 코드를 고치기 전에, 의심 가는 지점마다 실제 값을 확인합니다. 시도 2에서 Codex가 거친 과정입니다.</p>

```bash 시도 2의 진단 과정
# 실제 응답: 필드는 있지만 값이 null이다
$ curl -s localhost:3000/users/42 | jq '{id, name, avatarUrl}'
{ "id": "42", "name": "Kim", "avatarUrl": null }

# 컨트롤러: 저장소가 돌려준 user.avatarUrl을 그대로 쓴다
$ grep -n "avatarUrl" src/legacy/users.controller.ts
14:    avatarUrl: user.avatarUrl ?? null,

# 저장소: 쿼리가 id와 name만 읽는다
$ grep -n "SELECT" src/legacy/users.repository.ts
3:  const [row] = await db.query('SELECT id, name FROM users WHERE id = $1', [id]);

# DB: 값은 들어 있다
$ psql -c "SELECT avatar_url FROM users WHERE id = '42'"
              avatar_url
---------------------------------------
 https://cdn.example.com/avatars/42.png
```

DB에는 값이 있는데 쿼리가 그 컬럼을 읽지 않습니다. 진단은 “조회 쿼리가 `avatar_url`을 읽지 않는다”는 한 문장으로 정리되고, 진단이 구체적이면 수정도 작아집니다. 여기서는 `SELECT`에 컬럼 하나를 추가하면 됩니다.

**4. 같은 검사로 다시 확인합니다.** 고친 뒤에는 실패했던 검사를 그대로 다시 실행합니다. 통과하면 `verify.sh`는 다음 검사로 넘어가고, 다른 실패 메시지가 나오면 그 메시지로 1단계부터 다시 시작합니다. 메시지가 **그대로**라면 진단이 틀렸다는 뜻이므로, 고친 코드를 되돌리고 3단계로 돌아갑니다.

### 이 루프가 잘못될 수 있었던 지점

위의 기록은 매번 맞는 판단을 내린 경우입니다. 같은 실패 메시지를 받고도 다르게 판단했다면 루프는 다른 곳에서 끝났을 것입니다. 갈림길이 될 수 있었던 지점을 세 곳 살펴보겠습니다.

#### 갈림길 1: 테스트를 고쳐도 되는가 (시도 1)

시도 1에서 Codex는 테스트를 고쳐서 통과시켰습니다. 그런데 테스트를 고쳐 통과시키는 일은, 경우에 따라 코드가 아니라 채점 기준을 바꾸는 일, 즉 테스트 약화가 됩니다. 둘을 가르는 것은 **무엇을 고쳤는가**입니다.

| 테스트 변경 | 의미 | 판정 |
|---|---|---|
| 기대값에 새 필드 `avatarUrl`을 추가 (시도 1) | 새 요구사항을 테스트에 반영한다 | <span class="badge pass">허용</span> |
| 기존 필드 `name`의 기대값을 `displayName`으로 변경 (1장) | 깨진 동작에 기준을 맞춘다 | <span class="badge fail">약화</span> |
| 실패하는 테스트를 삭제하거나 건너뜀 | 기준 자체를 없앤다 | <span class="badge fail">약화</span> |

> [!주의]
> 중요한 테스트를 지우거나 승인 없이 요구사항을 바꿔서 얻은 통과는 성공이 아니라 평가 체계를 훼손한 것입니다. 이런 변경이 필요해 보이면 루프를 멈추고 사람에게 판단을 넘겨야 합니다.

#### 갈림길 2: 진단 없이 고칠 때 (시도 2)

<p class="keep-with-next">시도 2에서 진단을 건너뛰고, 메시지에 나온 <code>avatarUrl</code>이 있는 컨트롤러만 고쳤다면 기록은 이렇게 됩니다.</p>

```bash 원인에 닿지 않는 루프
# 시도 2
FAIL: /users/42 응답에 avatarUrl 값이 없음 (null 포함)
# 조치: user.avatarUrl ?? null을 user.avatarUrl로 바꾼다

# 시도 3
FAIL: /users/42 응답에 avatarUrl 값이 없음 (null 포함)
# 조치: 응답 매핑을 { ...user }로 바꾼다

# 시도 4
FAIL: /users/42 응답에 avatarUrl 값이 없음 (null 포함)
```

메시지가 바뀌지 않았다는 것은 조치가 원인에 닿지 않았다는 뜻입니다. 시도 3부터는 같은 자리를 맴도는 재시도입니다. 이때 필요한 것은 시도를 늘리는 것이 아니라 앞의 3단계처럼 값이 어디서 오는지 거슬러 올라가 보는 것입니다. 그래도 원인을 찾지 못하면 멈추고 지금까지의 시도를 보고합니다.

#### 갈림길 3: 판정을 무엇에 맡기는가

시도 2 직전에 `verify.sh` 대신 “한 번 더 꼼꼼히 봐 줘”라고 했다면, Codex는 컨트롤러 코드와 통과한 테스트를 다시 읽고 문제가 없다고 답했을 가능성이 큽니다. 처음 코드를 작성할 때 본 것을 “저장소가 값을 채워 준다”는 같은 가정 아래 다시 보기 때문입니다. 실제 서버의 응답은 그런 가정에 영향을 받지 않습니다. 모델의 자기 피드백만으로 결과가 나아졌다는 연구도 있지만, 신뢰할 만한 외부 신호 없이 스스로 고치게 하면 오히려 나빠질 수 있다는 보고도 있습니다. [@09][@11][@12] 판정은 실행 결과에 맡기고, 자기 검토는 보조로 쓰는 편이 안정적입니다. [@10]

실행 결과도 검사한 범위까지만 증명합니다. `verify.sh`는 값이 `null`이 아니라는 것까지만 확인할 뿐, 그 값이 올바른 이미지 주소인지는 확인하지 않습니다. 이런 한계는 1장의 완료 보고처럼 ‘확인하지 못한 것’에 적어 둡니다.

### 멈출 조건을 스킬에 되돌려 놓기

진단 순서와 갈림길에서 내려야 했던 판단은 다음 작업에서도 다시 쓰입니다. 스킬의 '실패했을 때' 항목에 넣어 두면, 다음 루프도 같은 순서로 진단하고 같은 자리에서 멈춥니다.

```diff SKILL.md (실패했을 때)
 ## 실패했을 때
 - 1에서 호출 지점을 찾지 못하면 추측해서 고르지 말고 멈추고 보고한다.
 - 5가 실패하면 대상 엔드포인트를 바꾸지 말고 원인을 고친다.
+- 실패한 단계(타입 검사, 테스트, 응답 확인)를 먼저 구분하고, 통과한
+  단계를 근거로 원인의 범위를 좁힌 뒤 실제 값을 확인하고 고친다.
+- 기존 필드의 테스트 기대값을 바꾸거나 지워야 통과한다면 바꾸지 말고 보고한다.
+- 같은 실패 메시지가 두 번 연속 나오면 멈추고 지금까지의 시도를 보고한다.
```

스킬은 이렇게 루프를 거칠 때마다 조금씩 구체적으로 바뀝니다. 다만 이 변경이 이후의 작업을 실제로 낫게 만드는지는 루프 한 번으로는 알 수 없습니다.
