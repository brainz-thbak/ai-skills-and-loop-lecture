서론의 Codex는 프런트엔드가 쓰지 않는 엔드포인트를 고치고, 테스트 통과와 호출 확인을 근거로 완료를 보고했습니다. 보고에 거짓은 없었지만 요구사항은 완료되지 않았습니다. 이후의 장들은 이 장면을 하나씩 다른 결과로 바꿔 왔습니다.

| 장 | 서론의 장면에 대해 한 일 | 남긴 것 |
|---|---|---|
| 1장 | 보고와 증거를 나누고, 증거가 무엇을 증명하는지 따졌다 | 증거가 붙은 완료 보고 |
| 2장 | 대상을 정하는 순서를 작업 프로토콜로 남겼다 | `SKILL.md`, `verify.sh`, `AGENTS.md` |
| 3장 | 실패 메시지로 진단하고, 멈출 조건을 정했다 | 스킬의 '실패했을 때' 항목 |
| 4장 | 스킬을 바꾼 결과를 여러 과제로 평가했다 | 평가 과제, 채점 스크립트 |
| 5장 | 매번 지켜야 할 검사를 작업 흐름에 묶었다 | `.codex/hooks.json` |

**스킬은 반복할 작업 방법을 정의하고, 평가는 그 방법이 실제로 결과를 낫게 하는지 확인하며, 피드백 루프는 평가에서 드러난 차이를 다음 행동과 다음 스킬에 반영합니다.** 이 연결이 없는 스킬은 문서에 가깝고, 실패가 아무것도 바꾸지 않는다면 피드백도 기록에 그칩니다.

### 작게 시작하기

처음부터 이 모든 것을 갖출 필요는 없습니다. 팀에서 자주 반복되고 성공 기준이 비교적 분명한 작업 하나를 고르는 것으로 충분합니다. API 응답 변경, 의존성 업데이트, 릴리스 점검처럼 이미 반복하는 작업이라면 기존의 테스트와 문서를 그대로 쓸 수 있습니다.

1. 과제 5~10개와 과제별 합격 기준을 먼저 정합니다. 스킬이 쓰이지 않아야 할 과제도 넣습니다.
2. 스킬 없이 과제를 실행해 기준선을 봅니다.
3. 대상, 순서, 완료 조건만 담은 최소한의 스킬을 쓰고 같은 과제로 평가합니다.
4. 반복되는 실패는 성격에 맞는 곳에 반영합니다. 판단이 필요한 절차는 스킬에, 매번 지켜야 할 검사는 훅과 CI에, 저장소에 대한 사실은 `AGENTS.md`에 둡니다.
5. 개선에 쓰지 않은 과제로 다시 확인합니다.

이 순서의 목적은 스킬을 도입하는 것이 아닙니다. **어떤 작업은 스킬보다 테스트 하나를 더하는 편이 낫고, 어떤 작업은 절차를 표준화할수록 비용이 줄어듭니다.** 어느 쪽인지는 평가 결과가 정하게 합니다.

### 점검할 질문

- 스킬이 필요한 요청과 필요하지 않은 요청을 구분했는가?
- 완료 기준을 고친 코드가 아니라 요구사항과 그 소비자 쪽에서 정했는가?
- 결과와 과정에 각각 확인할 수 있는 판정 기준이 있는가?
- 실행하지 않은 검사를 실행했다고 보고하지 않는가?
- 같은 실패가 반복될 때 멈추고 사람에게 넘기는 조건이 있는가?
- 스킬을 바꾼 뒤 같은 조건의 여러 과제로, 그리고 개선에 쓰지 않은 과제로 다시 평가했는가?
- 매번 지켜야 할 검사가 스킬에만 적혀 있지 않은가?

### 좋은 하네스

좋은 하네스는 에이전트에게 끊임없이 ‘더 신중하라’고 말하는 환경이 아닙니다. 필요한 정보를 찾을 수 있고, 필요한 검사를 실행할 수 있고, 실패 원인을 관찰할 수 있고, 검증되지 않은 결과를 검증된 것처럼 보고하기 어려운 환경입니다. OpenAI의 *Harness Engineering* 사례도 코드 생성 능력만이 아니라 저장소 문서의 탐색성, 테스트, 관측 가능성, 강제 가능한 규칙이 전체 결과에 기여한다는 관점을 제시합니다. [@06]

마지막으로 검토해 볼 질문이 있습니다. 팀의 반복 업무 가운데 어떤 작업을 가장 먼저 평가 가능한 절차로 바꿀 수 있을까요?
