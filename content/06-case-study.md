이제 서론의 장면을 처음부터 다시 따라가 보겠습니다. 요청은 같습니다. 프로필 화면에 이미지를 보여 주기 위해 사용자 조회 API 응답에 `avatarUrl`을 추가합니다. 달라진 것은 2장의 스킬, 3장의 피드백 루프, 4장의 평가 기준이 준비되어 있다는 점입니다.

### 대상을 요구사항에서 정합니다

스킬의 첫 단계는 코드 검색이 아니라 요구사항의 출발점을 찾는 일입니다. 프로필 화면의 데이터 요청 코드를 따라가면 프런트엔드가 호출하는 엔드포인트가 `GET /users/:id`라는 사실이 나옵니다. 이어서 같은 역할의 엔드포인트를 검색하면 `GET /api/v2/users/:id`와 `GET /user/profile`이 함께 나옵니다.

서론의 Codex가 놓친 정보가 바로 이 두 단계에서 드러납니다. 셋 가운데 무엇을 바꾸는지, 나머지는 어떻게 다룰지는 근거와 함께 보고에 남깁니다.

### 작고 검증 가능한 목표를 작성합니다

‘필드를 추가한다’는 요구사항만으로는 작업 범위가 모호합니다. 프런트엔드가 호출하는 `GET /users/:id`의 응답에 `avatarUrl`이 포함될 것, 기존 필드를 제거하지 않을 것, `avatarUrl`이 없거나 null인 데이터를 정확히 처리할 것, 프로필 화면이 새 계약을 받아들일 것 같은 **독립적인 성공 조건**이 필요합니다. 이 가운데 첫 번째 조건이 서론의 장면에는 없었습니다.

```ts
// 설명을 위한 API 계약 예시
export type UserResponse = {
  id: string;
  name: string;
  avatarUrl: string | null;
};
```

### 작업 과정에서 무엇을 확인해야 할까요?

스킬은 대상 엔드포인트 확인, 계약 비교, 소비자 탐색, 필요한 검사 선정, 결과 보고를 담당합니다. TypeScript 컴파일러는 타입 오류를 찾고, 계약 테스트는 `GET /users/:id`의 응답이 요구한 형식을 충족하는지 확인합니다. 프런트엔드 통합 테스트는 프로필 화면과의 실제 연결을 검사합니다. 테스트에 포함되지 않은 클라이언트나 외부 호출자는 **검증 범위 밖**이라고 남겨야 합니다.

에이전트가 서론에서처럼 `GET /api/v2/users/:id`를 먼저 고쳤다고 해 봅시다. 이번에는 계약 테스트가 `GET /users/:id`를 기준으로 하므로 실패합니다. 실패 로그는 응답에 `avatarUrl`이 없다는 사실과 어느 엔드포인트를 검사했는지를 함께 보여 주고, 에이전트는 대상을 바로잡은 뒤 다시 검증합니다.

대상을 바로잡은 뒤 프로필 컴포넌트에서 `avatarUrl.toUpperCase()`를 호출해 타입 오류가 나더라도 마찬가지입니다. 실패 로그가 수정할 위치를 알려 주고, 코드를 고친 뒤 타입 검사를 다시 실행하면 **현재 작업의 피드백 루프**가 완성됩니다.

### 같은 실수를 다음 작업에서 막습니다

작업이 끝난 뒤에는 5장의 질문이 남습니다. 같은 역할의 엔드포인트 때문에 대상을 잘못 고르는 일이 다음 분기에도 반복된다면, 정식 엔드포인트를 `AGENTS.md`에 적고, 스킬의 1·2단계를 유지하고, `GET /users/:id`의 계약 테스트를 CI에 두는 편이 맞습니다.

이 개선이 유효한지는 4장의 보류 과제처럼 **개선에 쓰지 않은 새 과제에서 평가**해야 합니다. 그때 비로소 작업 방법을 개선했다고 말할 근거가 생깁니다.
