이제 처음에 제시한 API 변경 요청을 다시 살펴보겠습니다. `GET /users/:id`에 `avatarUrl: string | null`을 추가하되 기존 클라이언트의 호환성을 유지해야 합니다.

### 작고 검증 가능한 목표를 작성합니다

‘필드를 추가한다’는 요구사항만으로는 작업 범위가 모호합니다. 기존 필드를 제거하지 않을 것, `avatarUrl`이 없거나 null인 데이터를 정확히 처리할 것, 프런트엔드 소비자 코드가 새 계약을 받아들일 것, 기존 사용자 조회 기능이 유지될 것 같은 **독립적인 성공 조건**이 필요합니다.

```ts
// 설명을 위한 API 계약 예시
export type UserResponse = {
  id: string;
  name: string;
  avatarUrl: string | null;
};
```

### 작업 과정에서 무엇을 확인해야 할까요?

스킬은 계약 비교, 소비자 탐색, 필요한 검사 선정, 결과 보고를 담당합니다. TypeScript 컴파일러는 타입 오류를 찾고, 계약 테스트는 API 응답이 요구한 형식을 충족하는지 확인합니다. 프런트엔드 통합 테스트는 실제 소비자와의 연결을 검사합니다. 테스트에 포함되지 않은 클라이언트나 외부 호출자는 **검증 범위 밖**이라고 남겨야 합니다.

가령 소비자 코드에서 `avatarUrl.toUpperCase()`를 호출해 타입 오류가 발생했다면, 실패 로그는 수정할 위치를 알려줍니다. 이 경우 코드를 수정하고 타입 검사를 다시 실행하면 **현재 작업의 피드백 루프**가 완성됩니다.

다음 분기에도 동일한 유형의 API 변경에서 소비자 누락이 반복된다면, 스킬에 모든 소비자 검색 절차를 명시하거나 CI에 계약 검사를 추가하는 편이 맞을 수 있습니다. 이 개선이 유효한지는 **새로운 API 변경 과제에서 평가**해야 합니다. 그때 비로소 작업 방법을 개선했다고 말할 근거가 생깁니다.
