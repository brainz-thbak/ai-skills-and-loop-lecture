스킬을 작성할 때 가장 먼저 결정할 것은 지침 문장이 아니라 **스킬이 해결할 반복 문제의 경계**입니다. 모든 개발 요청에 호출되는 범용 스킬보다, 공개 API가 변경될 때 소비자와 호환성을 검사하는 스킬은 언제 호출해야 하는지, 무엇을 검사해야 하는지, 성공을 어떻게 판정할지 정의하기 쉽습니다.

### 무엇을 어디에 배치해야 할까요?

Codex의 여러 설정 표면을 한 곳에 몰아넣으면 오히려 수정하기 어렵습니다. `AGENTS.md`는 저장소 전반의 공통 규칙과 탐색 지도로, `SKILL.md`는 특정 작업의 절차로, `references/`는 필요할 때 읽을 상세 규약으로, `scripts/`는 반복 가능하고 결정적인 실행으로 활용하는 구성이 실무적으로 유용합니다. **테스트와 CI는 지침의 또 다른 표현이 아니라 독립적인 판정 계층**이라는 점이 중요합니다. [@01][@02]

| 위치 | 적절한 책임 | 피해야 할 오용 |
|---|---|---|
| `AGENTS.md` | 저장소 구조, 공통 금지 사항, 필수 확인 명령 | 개별 업무별 긴 실행 대본 누적 |
| `SKILL.md` | 특정 작업의 트리거, 실행 단계, 완료 조건 | 모든 코딩 작업을 담당하는 만능 스킬 |
| `references/` | 계약, 호환성 규칙, 상세 체크리스트 | 매번 전부 읽도록 강제 |
| `scripts/` | 정적 검사, 파일 생성, 로그 수집 | 모델의 판단이 필요한 결정을 무리하게 고정 |
| Test / CI | 독립적 합격 기준, 병합 게이트 | 스킬이 ‘실행하겠다’고 약속하는 데만 의존 |

명시적인 호출도 가능하지만, 자연어 요청에서 어떤 스킬을 사용할지 선택하는 과정에는 `name`, `description`과 작업 맥락이 영향을 줍니다. 따라서 이름을 멋지게 짓는 것보다 **적용 조건을 구체적으로 쓰는 것**이 중요합니다. 또한 작은 설명으로 스킬을 발견하고 세부 지침을 나중에 불러오는 방식은 불필요한 컨텍스트 점유를 줄일 수 있습니다. [@01]

### 최소한의 API 변경 검토 스킬

<p class="keep-with-next">다음 스킬은 실제 Codex에 넣기 전에 저장소의 도구·테스트와 맞춰야 하는 교육용 예시입니다.</p>

```text Directory
.agents/skills/api-contract-review/
├── SKILL.md
├── references/
│   └── compatibility.md
└── scripts/
    └── verify.sh
```

```md SKILL.md
---
name: api-contract-review
description: 공개 API 응답 또는 공유 타입이 변경될 때
  소비자 영향과 하위 호환성을 검토한다.
---

# API Contract Review

1. 변경 전후의 API 계약을 비교한다.
2. 응답을 소비하는 코드와 공개 타입을 검색한다.
3. references/compatibility.md의 호환성 기준을 확인한다.
4. 검증 스크립트와 해당 계약 테스트를 실행한다.
5. 실행하지 못한 검사는 완료로 보고하지 않는다.
6. 변경 범위, 검증 증거, 남은 위험을 함께 보고한다.
```

좋은 스킬은 작업의 **입력**, **트리거**, **필수 단계**, **실패했을 때의 처리**, **종료 조건**을 비교적 짧게 설명합니다. 여기서 `verify.sh`는 실행 가능한 명령을 모아놓은 도구이지, 외부에서 신뢰를 보장해주는 장치가 아닙니다. 정말 중요한 검사는 스킬 외부의 CI에서도 동일하게 실행할 수 있어야 합니다.

### 스킬을 사용하지 않는 편이 나은 경우도 있습니다

스킬에도 관리와 유지보수 비용이 따릅니다. 길고 중복된 지침은 컨텍스트를 소비하고 충돌을 만들며, 오래된 제약은 모델의 판단을 방해합니다. OpenAI가 스킬과 지침 설계를 재검토한 사례 역시 “규칙을 더 많이 추가하면 더 좋다”는 가정을 경계하도록 합니다. [@07]

한 번만 수행할 작업에는 구체적인 요청이 충분할 수 있습니다. 저장소 전체가 반드시 지켜야 하는 조건은 `AGENTS.md`가 알맞고, 모델의 해석 없이 기계적으로 검사할 수 있다면 테스트나 린터가 더 확실합니다. **스킬이 필요한 경우는 여러 작업에서 재사용할 판단과 순서가 있을 때**입니다.
