1장 끝의 세 줄을 스킬로 옮기는 방법은 크게 두 가지입니다. 주의 사항을 늘어놓는 방법과, 작업의 순서와 끝을 정하는 방법입니다. 둘 다 `SKILL.md` 한 장이지만 에이전트의 행동은 크게 달라집니다.

### 같은 내용, 두 가지 스킬

```md 긴 프롬프트형 SKILL.md
---
name: api-guidelines
description: API 작업 가이드라인
---

API를 수정할 때는 항상 꼼꼼하게 확인하세요.
관련 코드를 충분히 살펴보고, 영향을 받는 부분이 없는지 주의하세요.
같은 기능을 하는 코드가 있을 수 있으니 조심하세요.
변경 후에는 반드시 테스트를 실행하고 결과를 확인하세요.
하위 호환성을 깨뜨리지 않도록 유의하세요.
```

틀린 문장은 없습니다. 하지만 서론의 Codex가 이 스킬을 읽었더라도 같은 결과를 냈을 것입니다. '꼼꼼하게', '충분히', '주의하세요'는 확인할 대상도 확인이 끝나는 시점도 정하지 않습니다. "같은 기능을 하는 코드가 있을 수 있으니 조심하세요"는 무엇을 하라는 말인지 알 수 없고, "테스트를 실행하고 결과를 확인하세요"는 서론의 Codex가 실제로 한 일입니다.

```md 프로토콜형 SKILL.md
---
name: api-response-change
description: >-
  기존 API 응답에 필드를 추가·변경·삭제할 때 사용한다.
  화면이나 클라이언트의 요구에서 출발해 실제로 호출되는
  엔드포인트를 확정하고, 그 엔드포인트로 완료를 검증한다.
  문서나 주석만 바꾸는 작업에는 쓰지 않는다.
---

# API 응답 변경

## 입력
- 변경을 요청한 화면이나 클라이언트
- 추가·변경할 필드와 타입

## 단계
1. 요청한 화면의 데이터 요청 코드에서 호출하는 엔드포인트를 찾는다.
2. AGENTS.md의 정식 엔드포인트 목록과 대조하고, 같은 역할의
   엔드포인트를 검색한다. 여럿이면 1에서 찾은 것을 바꾼다.
3. 응답을 바꾸고, 새 필드의 값이 어디서 오는지(조회 쿼리, 저장소)도
   함께 바꾼다.
4. 기존 필드의 이름·타입·null 여부를 바꿀 때는
   references/compatibility.md를 읽고 판정에 따른다.
5. scripts/verify.sh <1의 경로> <필드>를 실행한다.

## 실패했을 때
- 1에서 호출 지점을 찾지 못하면 추측해서 고르지 말고 멈추고 보고한다.
- 5가 실패하면 대상 엔드포인트를 바꾸지 말고 원인을 고친다.

## 완료 조건
- 5가 1에서 찾은 엔드포인트로 통과했다.
- 보고에 변경 대상, 변경하지 않은 같은 역할의 엔드포인트,
  실행한 검증, 확인하지 못한 것을 적었다.
```

<p class="keep-with-next">프로토콜형 스킬의 각 부분이 맡는 역할과, 그 부분이 빠졌을 때 서론의 장면에서 일어난 일을 나란히 놓으면 다음과 같습니다.</p>

| 요소 | 이 스킬에서 | 빠지면 |
|---|---|---|
| 트리거 | `description`의 적용 조건과 제외 조건 | 필요한 작업에서 쓰이지 않거나, 무관한 작업에서 쓰인다 |
| 입력 | 요청한 화면, 바꿀 필드 | 출발점이 코드 검색 결과가 된다 |
| 단계 | 대상 확정 → 대조 → 변경 → 호환성 → 검증 | 먼저 찾은 파일부터 고친다 |
| 실패 처리 | 호출 지점을 못 찾으면 멈춘다 | 그럴듯한 쪽을 골라 진행한다 |
| 완료 조건 | 1의 엔드포인트로 검증 통과, 보고 항목 | “테스트 통과”가 곧 완료가 된다 |

프로토콜형이 더 길지만, 늘어난 부분은 모두 '언제', '무엇부터', '어디서 멈추는지'에 관한 것입니다. 긴 프롬프트형에 주의 문장을 더 보태는 것으로는 이 차이가 메워지지 않습니다. 1장의 '증거가 붙은 완료 보고'는 이 스킬의 완료 조건을 따른 결과물입니다.

### 트리거는 `description`에 씁니다

스킬은 `/skills`나 `$api-response-change`처럼 직접 지정해 호출할 수 있습니다<span class="badge codex">Codex 전용</span>. 지정하지 않으면 Codex가 작업과 각 스킬의 `description`을 비교해 쓸지 판단합니다. 이때 Codex가 처음 보는 것은 스킬의 이름과 설명뿐이고, `SKILL.md` 본문은 쓰기로 정한 뒤에 읽습니다. [@18] 따라서 **언제 써야 하는지는 본문이 아니라 `description`에 있어야 합니다.**

| `description` | 판정 | 이유 |
|---|---|---|
| API 작업 가이드라인 | <span class="badge fail">부족</span> | 어떤 작업에 쓰는지 알 수 없다 |
| API를 변경할 때 꼼꼼히 검토한다 | <span class="badge warn">과함</span> | 범위가 넓어 무관한 API 작업에도 선택된다 |
| 기존 API 응답에 필드를 추가·변경·삭제할 때 사용한다. … 문서나 주석만 바꾸는 작업에는 쓰지 않는다. | <span class="badge pass">적절</span> | 적용 조건과 제외 조건이 모두 있다 |

### `SKILL.md`만으로 부족할 때: `references/`와 `scripts/`

`SKILL.md` 본문만으로 모든 것을 해결하려 하면 두 가지 한계에 부딪힙니다.

첫째는 **컨텍스트**입니다. Codex는 스킬을 고르면 `SKILL.md` 전체를 읽습니다. [@18] 판정 기준표나 스키마 같은 상세 자료를 본문에 모두 넣으면, 그 자료가 필요 없는 작업에서도 매번 컨텍스트를 차지합니다. 공식 문서는 `SKILL.md`를 간결하게 유지하고 상세 자료는 그 옆에 두라고 권합니다. [@01] Agent Skills 명세는 본문을 500줄, 5,000토큰 미만으로 유지하고 상세 자료는 별도 파일로 옮기라고 구체적인 기준을 제시합니다. [@19]

둘째는 **결정성**입니다. 본문의 단계는 문장이라 실행할 때마다 해석됩니다. “1에서 찾은 엔드포인트로 응답을 확인한다”는 단계도 에이전트가 매번 명령을 직접 조합하면 그 과정에서 대상이나 판정 방식이 달라질 수 있습니다. 공식 문서는 결정적인 계산이나 파일 처리가 필요할 때 스크립트를 쓰라고 합니다. [@01]

<p class="keep-with-next">이 두 한계를 위한 자리가 스킬 디렉터리 안의 <code>references/</code>와 <code>scripts/</code>입니다. Agent Skills 명세는 스킬의 내용이 세 단계로 나뉘어 읽힌다고 설명합니다. [@19]</p>

#### `references/`: 특정 단계에서만 필요한 자료

<p class="keep-with-next">호환성 기준은 기존 필드의 이름, 타입, null 여부를 바꿀 때만 필요합니다. 필드를 추가하기만 하는 작업이라면 읽을 필요가 없으므로 본문에서 분리합니다.</p>

```md references/compatibility.md
# 응답 호환성 기준

- 필드 추가: 허용. 클라이언트는 모르는 필드를 무시해야 한다.
- non-null → null 허용: 주의. 소비자에게 알리고 응답 스키마를 같은 변경에서 고친다.
- 필드 이름 변경: 금지. 새 필드를 추가하고 기존 필드는 유지한다.
- 필드 삭제: 금지. 사용 중단을 표시하고 두 릴리스 뒤에 삭제한다.
```

1장에서 본 `name`을 `displayName`으로 바꾼 정리가 이 기준의 셋째 항목에 해당합니다.

공식 문서는 `SKILL.md`에서 부속 파일을 가리킬 때 **언제 읽거나 실행해야 하는지**를 함께 적으라고 합니다. [@01] 명세는 경로를 스킬 루트 기준의 상대 경로로 쓰고, 참조는 `SKILL.md`에서 한 단계 깊이까지만 두라고 합니다. [@19] 그래서 프로토콜형 스킬의 4단계는 조건과 함께 씁니다.

```md SKILL.md (4·5단계)
4. 기존 필드의 이름·타입·null 여부를 바꿀 때는
   references/compatibility.md를 읽고 판정에 따른다.
5. scripts/verify.sh <1의 경로> <필드>를 실행한다.
```

#### `scripts/`: 매번 같은 방식으로 실행해야 하는 일

<p class="keep-with-next">응답 검증은 판단이 필요 없는 일입니다. 대상과 판정 방식을 스크립트로 고정하면 에이전트가 할 일은 인자를 넘기는 것뿐입니다.</p>

```bash scripts/verify.sh
#!/usr/bin/env bash
# 사용법: verify.sh <경로> <필드>    예: verify.sh /users/42 avatarUrl
# <경로>는 <필드> 값이 실제로 있는 대상을 가리켜야 한다.
set -euo pipefail
if [ $# -ne 2 ]; then
  echo "사용법: verify.sh <경로> <필드>" >&2
  exit 2
fi
path="$1"; field="$2"

pnpm typecheck
pnpm test

if ! body=$(curl -sf "localhost:3000${path}"); then
  echo "FAIL: ${path} 호출 실패. 로컬 서버가 떠 있는지 확인한다" >&2
  exit 1
fi
if ! jq -e --arg f "$field" '.[$f] != null' <<<"$body" > /dev/null; then
  echo "FAIL: ${path} 응답에 ${field} 값이 없음 (null 포함)" >&2
  exit 1
fi
echo "OK: ${path} 응답에 ${field} 있음"
```

명세는 스크립트가 스스로 완결되거나 의존성을 명시하고, 도움이 되는 오류 메시지를 내고, 경계 상황을 처리하도록 권합니다. [@19] 위 스크립트의 인자 검사와 실패 메시지가 그 역할을 합니다. 실패 메시지는 에이전트가 다음 행동을 정하는 근거가 되므로, 무엇이 왜 실패했는지 드러나야 합니다.

> [!주의]
> 스크립트를 늘리는 것이 늘 나은 것은 아닙니다. Codex 문서는 결정적인 동작이나 외부 도구가 필요하지 않다면 스크립트보다 지침을 우선하라고 하고, 플러그인 문서는 지침과 기존 도구로 안정적으로 해낼 수 있는 일에는 스크립트를 추가하지 말라고 합니다. [@01][@18]

엔드포인트를 찾는 1단계는 화면 코드를 읽고 판단해야 하므로 스크립트가 아니라 본문의 단계로 남깁니다.

#### 그 밖의 구성 요소

`references/`, `scripts/` 외에도 스킬에 둘 수 있는 것이 있습니다. 이 사례에서는 쓰지 않지만 알아 둘 만합니다. <span class="badge codex">Codex 전용</span> 표시는 Agent Skills 명세에는 없고 Codex에서 제공하는 기능입니다. 이 가운데 일부는 ChatGPT에서도 쓰입니다. [@18]

| 구성 요소 | 담는 것 | 쓰는 때 |
|---|---|---|
| `assets/` | 복사하거나 변형해 쓰는 템플릿, 이미지, 데이터 파일 [@01][@19] | 결과물의 형식을 고정할 때. 예: 1장의 완료 보고 양식 |
| `agents/openai.yaml` <span class="badge codex">Codex 전용</span> | `interface`(앱에 보이는 이름·설명·아이콘), `policy`, `dependencies`(필요한 MCP 서버) [@18] | 자동 선택을 막거나, 스킬이 MCP 서버를 써야 할 때 |
| 머리말 선택 필드 | `license`, `compatibility`, `metadata`, `allowed-tools`(실험적) [@19] | 라이선스나 실행 환경 요구 사항을 밝힐 때 |

`agents/openai.yaml`의 `policy`에서 `allow_implicit_invocation: false`로 두면 Codex는 요청을 보고 이 스킬을 알아서 고르지 않고, `$스킬이름`으로 직접 부를 때만 씁니다. [@18] 배포처럼 의도치 않게 실행되면 곤란한 작업에 맞습니다. `dependencies`는 필요한 도구를 쓸 수 있게 할 뿐 작업 지침을 대신하지는 않습니다. [@01]

머리말의 `name`은 소문자, 숫자, 하이픈만 쓸 수 있고 64자를 넘을 수 없으며, 스킬 디렉터리 이름과 같아야 합니다. [@19] 이 장의 `api-response-change`가 디렉터리 이름과 같은 이유입니다. Codex 문서가 필수로 명시하는 필드는 `name`과 `description` 두 가지입니다. [@18]

### 스킬 밖에 두는 것

스킬 디렉터리 바깥에도 이 작업과 관련된 정보가 있습니다. 어느 엔드포인트가 정식인지는 특정 작업이 아니라 저장소에 대한 사실이므로 `AGENTS.md`에 둡니다.

```md AGENTS.md (일부)
## API 엔드포인트
- 사용자 조회의 정식 엔드포인트는 `GET /users/:id`다.
  프로필 화면과 설정 화면이 사용한다.
- `GET /api/v2/users/:id`, `GET /user/profile`은 레거시다.
  새 필드를 추가하지 않는다.
```

<p class="keep-with-next">스킬 안팎의 위치별 책임을 이 사례에 대입하면 다음과 같습니다. [@01][@02]</p>

| 위치 | 맡는 것 | 이 사례에서 | 피해야 할 오용 |
|---|---|---|---|
| `AGENTS.md` | 저장소 전체에 해당하는 사실과 규칙 | 정식 엔드포인트 목록 | 작업별 절차를 쌓아 두기 |
| `SKILL.md` | 특정 작업의 트리거, 단계, 완료 조건 | 대상 확정과 검증 순서 | 모든 작업을 맡는 만능 스킬 |
| `references/` | 특정 단계에서만 필요한 상세 자료 | 호환성 기준 | 매번 전부 읽도록 강제하기 |
| `scripts/` | 판단 없이 반복할 수 있는 실행 | `verify.sh` | 판단이 필요한 결정까지 고정하기 |
| 테스트 / CI | 에이전트와 독립된 판정 | `GET /users/:id` 계약 테스트 | 스킬의 “실행하겠다”는 약속에만 의존하기 |

> [!주의]
> `verify.sh`는 에이전트가 실행할 때만 의미가 있습니다. 스킬이 선택되지 않거나 단계를 건너뛰면 검증도 일어나지 않습니다. 반드시 지켜야 하는 조건은 같은 검사를 CI에도 두어, 에이전트가 무엇을 했든 병합 전에 판정되도록 합니다.

### 스킬이 맞지 않는 경우

스킬에도 비용이 있습니다. 중복된 지침은 컨텍스트를 차지하고 서로 충돌하며, 오래된 제약은 모델의 판단을 방해합니다. 규칙을 늘릴수록 좋아진다는 가정은 성립하지 않습니다. [@07]

한 번만 할 작업은 구체적인 요청으로 충분합니다. 저장소 전체에 적용되는 사실은 `AGENTS.md`가, 기계적으로 판정할 수 있는 조건은 테스트나 린트가 맡습니다. 스킬은 **여러 작업에서 반복되는 판단과 순서**가 있을 때 씁니다. 이 사례의 대상 확정이 그렇습니다. 어느 엔드포인트가 정식인지는 `AGENTS.md`로 알 수 있지만, 이번 요청이 어느 화면에서 왔고 그 화면이 무엇을 호출하는지는 작업마다 새로 찾아야 합니다.
