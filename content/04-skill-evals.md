title: 스킬의 품질을 평가하려면 독립적인 기준이 필요합니다
---

한 번의 작업을 수정하는 루프는 비교적 직관적입니다. 더 어려운 문제는 **스킬을 변경한 뒤 후속 작업의 품질이 실제로 향상되었는지**를 확인하는 일입니다. ‘좋은 스킬 같다’는 인상 대신, 재현 가능한 평가 과제와 실행 기록이 필요합니다. OpenAI의 *Testing Agent Skills Systematically with Evals*는 스킬 평가를 결과물뿐 아니라 스킬 호출과 작업 과정, 출력 형식, 효율성까지 확장합니다. [@03]

### 무엇을 평가해야 할까요?

**Outcome**은 요구사항을 충족했는지, **Process**는 필수 검사와 도구 사용을 수행했는지, **Invocation**은 맞는 상황에서 스킬이 선택됐는지, **Efficiency**는 비용과 시간이 적절한지를 살핍니다. 예를 들어 스킬을 호출하고 모든 검사를 실행했더라도 API 호환성을 깨뜨리면 Outcome은 실패입니다. 반대로 우연히 결과가 맞았더라도 검증을 생략하면 Process에는 문제가 남습니다.

평가용 과제는 성공해야 하는 사례만 모아서는 안 됩니다. 스킬이 **호출되지 않아야 하는 사례**도 반드시 있어야 합니다. 문서 오탈자 수정에 무거운 API 회귀 스킬이 호출된다면 불필요한 비용이 발생하고, 실제 필요한 작업에서 호출되지 않는다면 안전장치로서의 의미가 약해집니다.

| 과제 | 요청 내용 | 스킬 호출 기대 | 독립적 평가 기준 |
|---|---|---|---|
| T1 | API 응답에 nullable 필드 추가 | 예 | 계약·소비자 테스트 |
| T2 | 공개 타입의 필드명 변경 | 예 | 영향 범위·호환성 판단 |
| T3 | API의 null 처리 변경 | 예 | null/undefined 경계 검사 |
| N1 | README 오탈자 수정 | 아니오 | 불필요한 검사 미실행 |
| N2 | 주석만 수정 | 아니오 | 기능 변경 없음 |

### Codex의 실행 기록으로 무엇을 알 수 있을까요?

`codex exec --json`은 비대화형 Codex 실행의 JSONL 이벤트를 기록하는 데 사용할 수 있습니다. 작업 마지막에 나온 자연어 요약이 아니라 **어떤 명령과 도구가 사용됐고, 어떤 결과물이 생성됐는지** 확인하기 위한 관측 수단입니다. 다만 JSON 이벤트 기록 자체가 합격 판정을 제공하는 것은 아닙니다. 평가기는 이 기록과 실제 산출물, 독립 테스트 결과를 함께 읽어야 합니다. [@03][@04]

```bash
# 실행별로 동일한 초기 저장소 상태를 준비한다.
# 경로와 프롬프트는 예시이며 사전 디렉터리 생성이 필요하다.
mkdir -p artifacts
codex exec --json "API 응답 변경과 영향 범위를 검토해줘" \
  > artifacts/api-change-run.jsonl
```

평가를 실제로 설계할 때는 **결정적 검사**를 먼저 둡니다. 프로세스 종료 코드, 테스트 결과, 변경된 파일, 필수 산출물의 스키마는 프로그램으로 검사할 수 있습니다. 설계의 타당성이나 위험 설명의 충분성처럼 정답이 하나가 아닌 항목에는 루브릭 기반 모델 평가를 보조로 사용할 수 있습니다. 오탐과 검토 비용까지 추적해야 한다는 점에서 코드 검증의 운영 문제와도 연결됩니다. [@13]

실험에서는 과제, 모델, 샌드박스, 초기 커밋, 테스트 환경을 가능한 한 동일하게 맞춥니다. 에이전트 실행에는 비결정성이 있으므로 **한 번의 성공을 근거로 일반화하면 안 됩니다.** 여러 과제와 반복 실행이 필요하고, 스킬을 튜닝하는 데 사용한 사례와 최종 검증용 사례를 분리해야 평가 데이터에 대한 과적합을 줄일 수 있습니다.

좋아진 것이 확인되더라도 어떤 비용을 지불했는지 살펴야 합니다. 예를 들어 성공률이 오르는 동시에 작업 시간이 크게 늘거나, 관련 없는 요청에서도 무거운 스킬이 호출된다면 운영상의 개선이라고 단정하기 어렵습니다. **품질은 성공률만으로 결정되지 않습니다.**
