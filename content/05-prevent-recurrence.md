작업 중 발견한 버그를 수정하는 일과, 같은 종류의 버그가 다시 발생하지 않도록 개발 환경을 바꾸는 일은 다릅니다. 첫 번째는 현재 산출물을 고치는 것이고, 두 번째는 다음 작업의 실패 가능성을 낮추기 위한 투자입니다. 두 번째 변화는 **어떤 계층에 저장할지를 판단하는 것**부터 시작합니다.

API 변경 후 소비자 코드를 누락한 문제가 한 번 발생했다면 해당 코드를 고치고 테스트를 추가하면 충분할 수 있습니다. 하지만 API 변경 때마다 비슷한 누락이 발생한다면 소비자 검색 절차를 스킬에 추가하거나, 계약 테스트를 CI에 추가하는 편이 낫습니다. 프로젝트 구조에 대한 정보가 오래됐다면 `AGENTS.md`나 참조 문서를 갱신해야 합니다. 기억을 많이 남기는 게 목적이 아니라 **다음 작업에서 같은 종류의 실수를 더 어렵게 만드는 것**이 목적입니다.

Codex Hooks는 실행 이벤트에 검사·로깅 등의 처리를 연결하는 선택적 자동화 지점입니다. 특정 시점의 피드백을 더 빠르게 수집할 수 있지만, 핵심 보증을 Hook 하나에만 의존하면 Hook 실행 조건이나 권한이 바뀌는 순간 보증이 사라질 수 있습니다. 반드시 지켜야 하는 검사는 CI 같은 별도의 검증 단계에도 두는 편이 견고합니다. 사용 가능한 이벤트와 동작은 **설치된 Codex 버전의 공식 문서로 확인**해야 합니다. [@05]

```json package.json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "verify": "pnpm typecheck && pnpm test"
  }
}
```

위 `package.json` 예시는 `typescript`, `vitest` 등 의존성과 설정이 존재한다는 전제가 있어야 동작합니다. 중요한 것은 `verify`라는 명령의 이름이 아니라 **Codex가 실행한 검사와 팀의 병합 기준이 같은 근거를 사용하도록 만드는 것**입니다.

### 경험은 어디에 남겨야 할까요?

Reflexion은 실패의 교훈을 언어적 기억으로 다음 시도에 전달하는 접근을, ACE는 작업 경험에 따라 플레이북을 점진적으로 갱신하는 접근을 연구합니다. [@14][@15] 이들은 지속적 개선의 다양한 형태를 보여주지만, 장기 메모리 데이터베이스를 모든 팀에 도입해야 한다는 뜻은 아닙니다.

한 번 있었던 특이한 장애는 이슈로 기록할 수 있습니다. 재사용되는 지식은 참조 문서에, 반복 가능한 작업 절차는 스킬에, 반드시 위반을 차단할 조건은 테스트·Lint·CI에 남길 수 있습니다. **무엇을 저장하느냐보다 무엇을 재사용할 때 유효한가가 중요합니다.**
